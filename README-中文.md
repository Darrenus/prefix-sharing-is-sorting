# 前缀共享其实是个排序问题

一句话：**大模型服务里"给检索到的片段排个序"这件小事，背后是一个没人做过的组合优化问题；
现在所有系统的做法（用一个全局固定顺序）只在最退化的情况下是对的，一般情况下差距可以无限大。**

---

## 1. 问题是怎么冒出来的

现在的推理引擎（vLLM、SGLang 这些）复用 KV cache 的规则很硬：**只认前缀完全相同**。
两个请求从第一个不一样的 token 开始，后面全部要重算。

这条规则本身没问题，它就是前缀缓存能work的原因。但它悄悄制造了一个优化问题：

越来越多的 prompt 不是人打出来的一句话，而是系统自己拼起来的**一堆零件**：

- RAG 检索回来的若干段落
- agent 的工具定义
- few-shot 例子
- 跨轮次带过来的记忆条目

零件是**一个集合**，prompt 是**一个序列**。中间必须有人决定顺序。而这个顺序是**白给的自由度**
——模型看到的信息一样，先放哪段后放哪段不影响答案。

今天所有系统都用同一个办法定这个顺序：按检索得分排、按文档 ID 排、按热度排。
**一个全局顺序，所有请求通用。**

我想问的就是：这样对吗？

---

## 2. 答案

**只有在每个请求最多 2 个片段时才对。到 3 个就开始错，而且错得可以无限大。**

### 最小反例（小到可以手算）

4 个片段 a, b, c, d。4 个请求，每个请求要 3 个片段，正好是全部四种组合：

```
请求1: {a,b,c}    请求2: {a,b,d}    请求3: {a,c,d}    请求4: {b,c,d}
```

**允许每个请求自己排**，最优是 8：

```
请求1 → a b c        请求3 → c d a
请求2 → a b d        请求4 → c d b
        ↑ 共享 "ab"          ↑ 共享 "cd"
```
前缀树一共 8 个节点：a, ab, abc, abd, c, cd, cda, cdb。

**如果必须用一个全局顺序**，最优是 9，做不到 8。原因很直白：
上面那个解要求 1、2 号共享 "ab"（意味着 a,b 要排在 c,d 前面），
同时 3、4 号共享 "cd"（意味着 c,d 要排在 a,b 前面）。一个全局顺序不可能同时满足。

我穷举验证过：这是**唯一**的最小反例。

### 差距能有多大

把上面的例子推广：n 个片段，n 个请求，第 i 个请求要"除了第 i 个之外的全部片段"。
（这就是 RAG 里重叠度很高的那种典型情况——任意两个请求只差两个片段。）

- 全局顺序：**n²/2**
- 自由排序：**n·log₂n**

| n | 自由排序 | 全局顺序 | 差距 |
|---:|---:|---:|---:|
| 16 | 64 | 135 | 2.1 倍 |
| 64 | 384 | 2079 | 5.4 倍 |
| 256 | 2048 | 32895 | 16 倍 |
| 4096 | 49152 | 8390655 | **171 倍** |

## 2.5 【新】主定理：排列其实根本不是这个问题的主角

这是这一轮做出来的核心结果，它把整篇文章的骨架换掉了。

对每个片段 x，记 **S_x = 需要这个片段的所有请求**。给请求集合建一棵二叉层次树 H，
记 **t_x(H) = 把 S_x 完整覆盖住所需要的、H 里最大的簇的个数**（就是"S_x 在这棵树里被切成几块"）。

**定理：**

```
最小前缀树代价 = min over 所有二叉层次树 H 的  Σ_x  w(x) · t_x(H)
```

等价写法（m 个叶子的二叉树内部节点恰好 m−1 个）：

```
最小代价 = Σ_i |R_i|  −  max over H 的  Σ(每个内部节点的公共交集大小)
```

**这句话的意思是：排列消失了。** 给每个请求排序，等价于**给请求集合选一棵层次树**，
顺序只是从树上读出来的副产品。对做系统的人，可操作的说法是：

> 别再想"片段该怎么排"，去想"请求该怎么聚类"。

而 t_x 这个量，恰好就是**线段树里一次区间查询碰到 O(log n) 个节点**的那个量
（规范分解大小）。所以整个问题可以一句话说完：
**每个片段，每被切碎到一个新的簇里，就要重算一次。设计那棵树，让总的碎片数最小。**

证明两个方向都很干净。我原来担心的"兄弟节点必须用不同片段开头"（Hall 定理/相异代表系）
其实是**多余的顾虑**——前缀树本来就允许两个兄弟撞到同一个片段时自动合并，合并只会更便宜。
想通这点之后证明就通了。

### 这个定理带来什么

**一、精确算法从 m≤7 提到 m≤16。** 子集 DP，O(3^m)，m=16 只要 1.7 秒。
本文所有精确数字都重算过一遍。

**二、归并排序那件事有了真正的解释。** 对 leave-one-out 家族，S_x 是"除 x 外的全部请求"，
而**一个叶子的补集在二叉树里恰好被切成"根到该叶路径上的兄弟子树"，个数 = 该叶的深度**。
所以最优代价 = **二叉树的最小外部路径长度**。这是个经典量，而它正好也是比较排序的下界——
归并排序数出现在这里不是巧合，是同一个量。原来要一页的证明，现在两行。

**三、说清楚了全局序输在哪。** 一个全局片段顺序其实也诱导一棵层次树（不断按"优先级最高的
未发片段"劈开）。所以"全局序"= 把层次树限制在"由固定优先级生成"的那一类里。
这正好就是**决策图里 OBDD（固定变量序）和 FBDD（每条路径可以有自己的序）的区别**，
只不过搬到了缓存布局上。

**四、我的贪心算法有了解释。** 它就是这个"savings"目标的自然贪心（每次合并公共交集最大的两簇）。
用新的精确求解器实测：在 RAG 形状的实例上，贪心**平均只比真最优差 2.6%**（最坏 11%）。
这条很重要——它说明和全局序之间那 17–20% 是**真实空间**，不是我算法不行。

## 3. 为什么最优解正好是归并排序

上面那个 n·log₂n 不是个近似估计，是精确值：

```
S(n) = n + S(⌈n/2⌉) + S(⌊n/2⌋),   S(1) = 0
```

这就是**归并排序的递推式**。算出来的数列 0, 2, 5, 8, 12, 16, 20, 24, 29… 是 OEIS 上的
A001855——二分插入排序/归并排序的最坏比较次数——平移 n−1。

所以可以这么说：

> **这类负载最优的 KV cache 布局，就是归并排序的递归树。
> 而"用一个全局顺序"是缓存布局界的冒泡排序：人家 n log n，你 n²。**

我用两种独立方法验证过（暴力精确求解器 n≤6，递推穷举 n≤40，闭式 n≤4000），全部吻合。

## 4. 一个反直觉的坑

看完上面，最自然的算法是：每一层挑覆盖请求最多的那个片段，分组，递归下去
（就是贪心命中集，set cover 的标准玩法）。**这个算法在这里是灾难。**

在上面那个家族里，每个片段都被 n−1 个请求需要，所以贪心每次只剥掉一个请求，
退化成 Θ(n²)——n=64 时算出来 2079，和全局顺序一模一样，而最优是 384。

**教训：这里要的不是"每层分叉少"，而是"每层分得均匀"。**
set cover 的直觉和分治的直觉在这里指向相反方向，分治赢。

## 5. 能用的算法

**凝聚式公共前缀层次聚类**：每个请求先当成一个簇（签名=它的片段集合），
反复合并"公共交集最大"的两个簇，合并后的签名就是那个交集。
然后自顶向下走这棵树，每个节点吐出"在这一层才变成公共的"那些片段。

- 复杂度 O(m² log m)，用 bitset 做交集，没有超参
- 在上面那个对抗家族上**正好等于最优**（n=16/32/64 给出 64/160/384）
- 在合成 RAG 负载上，比"按热度全局排序"这个生产实践**省 17–20% 的 prefill**

## 5.5 【新】贪心至少拿到最优节省的一半（Phase 1 闭合）

有了结构定理，算法问题变成了一个干净的问题，而且有干净的答案。

**定理**：记一棵层次树的节省为 `SAV(H) = Σ(每个内部节点的公共交集权重)`。凝聚贪心（每次合并
公共交集最大的两个簇）满足

```
SAV(贪心) ≥ (1/2) · SAV(最优)
```

对任意权重成立，而且 **1/2 不能再改进**。

### 证明的两个关键点

**第一，贪心的合并值是单调不增的。** 把 A、B 合并成 C 之后 `I(C) = I(A)∩I(B)`，所以 C 和任何
其他簇 D 配对的值不超过 `w(I(A)∩I(D))`——那个值上一步就已经在桌面上了。没被动过的配对值不变。
所以 `g₁ ≥ g₂ ≥ … ≥ g_{m−1}`。

**第二，逐阈值计数。** 固定 θ。因为节点越往下交集越大，最优树里"值 ≥ θ"的内部节点构成若干
**互不相交的子树** T_j，叶集 L_j 满足 `w(I(L_j)) ≥ θ`。

现在看贪心走到第 `t* = G(θ)+1` 步：此时所有可选配对的值都 < θ。那么**不可能有两个当前贪心簇
同时整个落在同一个 L_j 里**——否则这一对的值 ≥ θ，矛盾。所以**每个 L_j 最多吞下一个完整的
贪心簇**，其余碰到 L_j 的簇都必须"伸到 L_j 外面"，因而大小至少是 2。数一下就得到

```
A(θ) ≤ 2(t*−1) = 2G(θ)
```

再对 θ 做层饼积分，定理即得。

### 紧性和实测

当每个片段恰好被两个请求共享时，任何含 3 个以上叶子的节点交集为空，节省退化成
"兄弟对之和"——**这就是最大权匹配**，而贪心匹配在最坏打破平局下恰好是 1/2。
四请求的反例：`{0123},{14},{2578},{46}`，贪心拿 1，最优是 2。

实测：3000 个随机加权实例，违反定理的 **0 个**，违反证明引擎那条逐阈值不等式的也是 **0 个**。
另外用退火专门去搜贪心的最坏情况，约 15000 个实例，**最高只到 1.83**——说明 1/2 那个最坏
需要对抗性平局，正常实例上贪心离最优只有 2.6%。

### 必须说清的局限

**这是对"节省"的保证，不是对"总代价"的保证。** 节省才是运营上关心的量（到底省了多少 prefill），
但从 `SAV ≥ SAV*/2` 只能推出 `COST(贪心) ≤ (COST* + 无共享代价)/2`，而无共享代价和最优的比值
是无界的。所以 **MPT 本身有没有常数近似，仍然开放。**

### 附带产物：一个多项式时间可算的下界

每个内部节点满足 `w(I(v)) ≤ w(R_i ∩ R_j)`（i、j 取自它的两棵子树），而每个内部节点各取一对
恰好构成请求集上的一棵生成树。所以

```
最优节省 ≤ 最大生成树权重（边权 = 两请求交集权重）
```

于是 `最优代价 ≥ Σ|R_i| − 最大生成树`。这在 m 大到 O(3^m) 精确算法跑不动之后，是唯一能用的
最优性标尺（实测平均松 1.45 倍，最坏能松到 Ω(m)，但它是个真界）。

## 6. 必须诚实说的部分：在线场景没那么好

离线能拿到 17–20%，但线上是流式的。我试了两种在线做法：

**（a）先学一个策略再套用到后来的请求** —— 完全没用，−1% 到 +4%。

**（b）在每个 serving batch 内部做聚类**（架在一个持久 radix 树上）—— 有用，但要窗口够大。
扫了一遍前瞻窗口 W：

| 负载 | W=1 | 8 | 32 | 128 | 512 | 2048 | 离线 |
|---|---:|---:|---:|---:|---:|---:|---:|
| k=8 | 7.2% | 7.2% | 6.8% | 6.4% | 7.3% | 10.9% | **14.4%** |
| k=16 | 5.4% | 5.4% | 5.3% | 5.6% | 8.0% | 13.2% | **17.4%** |
| k=10 | 10.4% | 10.4% | 9.9% | 9.0% | 11.4% | 16.5% | **20.0%** |

**曲线的形状才是结论**：从 W=1 到 W≈128 是平的甚至略降，过了 512 才开始爬。
W=1 时那 5–10% 根本不是"自适应"带来的，是"在活跃前缀树里找最深匹配"带来的
（这基本就是 CacheWeaver 已经在做的事）。真正的自适应收益要几百个并发请求才出现。

中间那个下凹是关键线索。**全局顺序本质是一个"约定"，而约定的作用恰恰是让永远不会碰面的
双方也能达成一致。** 一旦每个请求自己挑顺序，两个本来能共享前缀的请求就可能岔开，
除非你能同时看到足够多的请求把它们协调起来，否则岔开的损失大于局部收益。
小窗口是**付了协调的代价，却没买到协调**。

实用结论：
- 并发几百以上，或者有任何离线/批处理路径 → 值得做，省 10–20% prefill
- 一次就一两个请求 → 保持全局约定，力气花在最深匹配上

## 6.5 【新】真实检索数据（Phase 2）

前面全是合成数据。这一节换成真的：BEIR 语料上跑 BM25，真实段落当 chunk，
用 `cl100k_base` 真实数 token。一个请求 = 一个查询检索回来的段落集合，代价 = 总 prefill token。

### 先问：真实检索里到底有没有共享空间

NFCorpus（3633 段落，2921 查询，k=8）：检索结果覆盖 2857 个不同段落、共 8472 个槽位，
**去重 2.97 倍**，**68.7% 的段落被不止一个查询要**，平均 |S_x| = 2.76。

**有重叠。问题是重叠有没有变成前缀重叠。**

### 答案：今天基本没有

生产 RAG 按相关性排序拼接，那是个**每请求各自的顺序，不是共享的顺序**。
NFCorpus 上它只把 6% 的 prefill 变成缓存命中。而一个统一的全局约定（按语料级热度排）
能做到 13%——**这本身就是全文论点的缩影：没有协调的"每请求自由"比一个约定更差。
买到复用的是协调，不是自由。**

三个语料 × 三个检索深度（占无共享 token 的比例，越低越好）：

| 方法 | NFC k=5 | NFC 8 | NFC 16 | SciFact 5 | SciFact 8 | SciFact 16 | FiQA 5 | FiQA 8 | FiQA 16 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 相关性排序（生产） | .844 | .885 | .924 | .818 | .867 | .918 | .967 | .979 | .990 |
| 全局序按文档 id | .789 | .831 | .874 | .792 | .837 | .900 | .936 | .949 | .966 |
| 全局序按热度 | .723 | .775 | .832 | .714 | .778 | .850 | .842 | .869 | .906 |
| 在线最长前缀匹配 | .703 | .749 | .800 | .695 | .752 | .831 | .834 | .861 | .898 |
| 逐层贪心命中集 | .641 | .661 | .692 | .652 | .690 | .732 | .799 | .814 | .848 |
| **凝聚层次（本文）** | **.607** | **.605** | **.591** | **.625** | **.640** | **.643** | **.786** | **.798** | **.818** |
| 生成树下界 | .490 | .488 | .465 | .526 | .546 | .553 | .660 | .687 | .713 |
| **比生产实践节省** | **−28.0%** | **−31.6%** | **−36.1%** | **−23.6%** | **−26.2%** | **−29.9%** | **−18.7%** | **−18.5%** | **−17.3%** |

这张表里有三件事值得停一下。

**一、生产实践的前缀复用率，检索得越多反而越差。** 相关性排序在 NFCorpus 上随 k 从 5 到 16
走的是 .844 → .885 → .924，FiQA 上是 .967 → .990——**k=16 配大语料时，前缀缓存基本已经失效了。**
我们的方向相反：.607 → .605 → .591。

机制正是定理 5 讲的那件事：k 越大集合重叠越多，但"两个请求的整个**有序**前缀都一致"的概率
崩塌得更快。**这是理论预测直接出现在日志里**——自适应与全局序的差距随请求规模变宽，
实测 k=5/8/16 分别是 −28%、−32%、−36%。

**二、收益大小跟检索集中度走，我把不好看的那头也报出来。**
NFCorpus 是 2921 个查询打进 3633 个段落（k=8 时去重 6.7 倍，92% 的段落被多次要），给 −32%。
FiQA 是 2500 个查询打进 57638 个段落（去重 1.8 倍，38% 共享），给 −18.5%。
**大而稀疏的语料会把收益砍掉一半——但 18% 的 prefill 仍然值得拿。**

**三、算法不是瓶颈。** 采样真实的重叠请求组（都检索到某个热门段落的那些请求，上限 13 个），
用 O(3^m) 精确求解：贪心比最优只高 **0.05%**（NFCorpus，最差组 2.46%）、**0.00%**（SciFact，
最差 0.16%）。定理 6 保证的是最坏 2 倍，**真实检索结构上贪心基本就是精确的**——
剩下那段到下界的距离是下界本身松，不是启发式差。

### 重排会不会伤答案质量

会有风险（"lost in the middle"）。我没跑质量评测，而是**给这个约束定了价**：
把最相关的 top-t 个段落按序钉死在 prompt **末尾**（贴近问题，也是实践里的放法），
只对其余部分自由重排。这也正好是缓存友好的形状：**共享前缀 + 个性化后缀**。

| 相比生产实践的节省 | 完全自由 | 钉 top-1 | 钉 top-2 | 钉 top-3 |
|---|---:|---:|---:|---:|
| NFCorpus k=8, 2921 查询 | −31.6% | −23.4% | −17.3% | −12.9% |
| SciFact k=8, 1109 查询 | −26.2% | −19.4% | −13.2% | −7.9% |

**约束下收益仍然在**：连钉三个最相关段落都还剩 8–13%，只钉最相关那一个还剩 19–23%。

| NFCorpus 比最好全局序 | −5.9% | −6.0% | −6.6% | −7.0% | −9.5% | **−21.9%** |
| SciFact 比生产 | −14.8% | −13.3% | −15.4% | −16.7% | −20.3% | **−26.2%** |

**上一轮我用合成数据得出"在线基本拿不到收益"，那个结论是错的。** 真实轨迹上曲线是单调上升的，
而且 W=1（完全在线、不攒批）就已经比生产实践省 15–18%。

合成生成器把困难制造出来了——它给每个主题一个可互换的段落池，导致持久前缀树没有稳定结构可抓。
这是我手上最直接的证据：**在这个问题上合成负载不能替代真实负载。**

上一轮的解读里活下来的是**曲线形状的含义**：自适应是拿前瞻换的。全局序是个"约定"，
而约定的作用正是让永不碰面的请求也能一致；窗口太小就是付了协调的代价没买到协调。
真实流量的可利用结构比我的生成器多得多，所以那个门槛低很多。

拆解也很干净：15–18% 那部分不需要任何前瞻，来自"放弃相关性排序、改成在活跃前缀树里找最深匹配"
（大致就是 CacheWeaver 在做的事）；**自适应那部分**——也就是主定理管的那部分——
在窗口过几百之后再加 5–10 个点，离线时大约翻倍。

## 6.8 【新】有限缓存（Phase 3）

主定理假设缓存装得下整棵树。真实缓存会驱逐，而且**排序和驱逐是耦合的**。这一节把这个洞补上。

模拟器按 SGLang/vLLM 的真实行为写：缓存节点必须连着祖先，驱逐从**最近最少使用的叶子**开始。

### 先看坏消息：按真实查询顺序服务，优势被容量卡住

NFCorpus（k=8，2921 查询，一个请求 ≈ 6036 token），我们相对生产实践的优势：

- 缓存 = 1 个请求：只剩 **−3.0%**
- 64x：−11.3%
- 256x：−23.5%
- 1024x 以上才拿满 **−31.7%**

而且 16x 以下所有方法都逼近无共享的账单——**那个容量下前缀缓存本身就已经失效了**，任何布局都救不回来。

排名倒是从没反转过。我原本猜"把共享集中在树顶"的贪心命中集会更抗驱逐，**猜错了**。

### 好消息：层次树同时也是一份调度表

**定理 7**：按 trie 的 DFS 顺序服务请求（等价于：把请求流按铺好的序列做字典序排序），
那么一个容量只有 `max_i w(R_i)`——**一个请求的上下文**——的 LRU radix 缓存，
就能拿到**和无限缓存完全一样**的代价。对任何布局都成立。

**证明**：DFS 顺序下，任一 trie 节点底下的请求是**连成一块**被服务的，所以该节点在它那块开始时
创建、在结束后再不会被用到。看服务请求 i 的那一刻：任何不在 i 的根到叶路径上的缓存节点，
要么属于已经结束的块（再不会用到），要么属于还没开始的块（那它还没被创建）。
所以"活着"的集合恰好是 i 的那条根路径，重量不超过 `max_i w(R_i)`。
服务 i 会触碰整条路径使其成为最新，LRU 只会淘汰已经死掉的节点。∎

实测确认，而且界几乎是紧的：**0.9x 就已经精确**，0.75x 差 +0.01%，0.5x 差 +0.8%，
0.25x 才崩到 +18%。包括生产实践的相关性排序在内，**每种布局都在 1x 处拿到了自己的无限缓存数字**。

### 最有用的结论：缓存容量和重排窗口是互相替代的

线下能重排整个流，线上只有一个窗口 W。在 W 个到达里排序，相对无限缓存最优的超出量：

| W \ 缓存 | 1x | 4x | 16x | 64x | 256x | 1024x |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 58% | 57% | 54% | 42% | 19% | **0%** |
| 128 | 52% | 52% | 52% | 40% | 19% | **0%** |
| 512 | 38% | 38% | 38% | 38% | 18% | **0%** |
| 2048 | 14% | 14% | 14% | 14% | 14% | **0%** |
| 全部 | **0%** | **0%** | **0%** | **0%** | **0%** | **0%** |

（参照：生产实践按流式顺序、4x 缓存，是 +63%。）

这张表是 **L 形**的——超出量基本等于 `min(窗口的函数, 容量的函数)`。

> **缓存容量和重排窗口是互相替代的：两者你需要一个，不需要两个。**
> 有大前缀缓存的栈可以完全不管顺序；缓存只有一个请求大小、但有深重排队列的栈，
> 拿到的数字一模一样。两个都买，什么也不多买。

这也顺带说清了 **SGLang 的 cache-aware 调度器在做什么**：按最长前缀匹配重排等待队列，
是对"trie 的 DFS 顺序"的贪心近似。定理 7 指出了它在逼近的那个精确目标，
并且说明命中它之后缓存容量就不再重要。两件事是可以叠加的：
**我们的层次树给出布局，它的 DFS 遍历给出调度，两者出自同一棵树。**

## 6.9 【新】文献核查的两个结果（Phase 4）

系统性扫了三条线（LLM 服务 / 数据库 / 组合与理论）。两件事必须说。

### 一、我要修正定理 7 的定位

**SGLang 已经有一个叫 `DFS_WEIGHT` 的调度策略**，按请求在 cache tree 里的位置分组——
那本质上就是 DFS 顺序的启发式版本。所以"按 DFS 顺序服务"对做系统的人不是新想法。

定理 7 新的部分是**精确刻画**：它说明那个启发式在逼近的目标到底是什么（trie 的 DFS 序），
以及命中它值多少——**所需缓存容量塌缩到一个请求的上下文，而且是精确等于无限缓存代价，对任何布局成立**。
由此得到的"容量和窗口互为替代"那条，我没在任何地方见人说过。

两件事是可叠加的：**我们的层次树给布局，它的 DFS 遍历给调度。**
一个已经在跑 `DFS_WEIGHT` 的调度器，等于在跑这篇论文的一半——只是布局是别人选的。

### 二、一个成立但很弱的推论（我按它的真实分量写）

如果 {S_x} 有**连续一性质**（请求能排在一条线上，使每个 chunk 被一段连续的请求需要——
也就是"完美主题局部性"长什么样），那么在那条线上建平衡树，每个 S_x 就是一个区间，
而区间的规范分解不超过 `2⌈log₂m⌉` 个节点。于是

```
最优 ≤ Σ_x w(x) · min(|S_x|, 2⌈log₂m⌉)
```

而这样的顺序可以用 **PQ-树线性时间找到**（Booth–Lueker 1976）。

**但我要诚实说两点**：这个界很松（m=16 的随机 C1P 实例上，精确最优是 35，界给 121）；
而且**在我的真实检索轨迹上它是空的**——平均 |S_x| 只有 2–6，而 2⌈log₂m⌉ ≈ 22，min 永远取 |S_x|。

它只在**真正的热 chunk** 上才有内容：共享系统提示、工具定义、所有人都检索到的那份文档——
那里它说重算次数是共享度的**对数**而不是线性。

### 新颖性核查的结论

- "选一棵树来最小化一族集合的规范分解总大小"——**没找到前人做过**。
- 层次聚类那边：我的目标是叶集的**集合函数**，而 Dasgupta 那一族（以及它的可接受性刻画）
  要求目标是子簇**基数**的函数。落在那个族之外。
- 最接近的先行工作是数据库那篇 Guravannavar 等 2006（给定查询计划树上选排序序，
  NP-hard + 2 近似）——**差别正是主定理的内容**：他们的共享结构是给定的，我的共享结构本身是决策变量。

## 7. 还开放的问题

1. **差距上限到底是多少？** 我证了 Ω(k/log k) 下界，平凡上界是 O(k)。
   但小规模穷举发现 leave-one-out 家族**不是最坏的**：k=4 时找到一个 6 请求的实例
   比率 1.417，超过同 k 下 leave-one-out 的 1.167。真相是 Θ(k) 还是 Θ(k/log k)？
2. **【已解决一半】** 贪心对"节省"是紧的 1/2 近似（见 5.5）。但对"总代价"能不能常数近似，
   仍然开放——k=2 的特例反而是容易近似的，所以困难如果存在，一定来自更大的请求。
3. **带前瞻的在线竞争比是 W 的什么函数？** 第 6 节说明这条曲线不平，但形状不知道。
4. **放宽"精确前缀"之后呢？** CacheBlend 那类方法用一点精度换位置无关的复用，
   那时候对象就不是前缀树了，组合结构完全变掉。

（原来的第 4 条"有限缓存没建模"已经由 6.8 节解决。）
